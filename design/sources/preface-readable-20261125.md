## 1. 编写背景

### 1.1 行业背景：智能体已从“框架搭建”进入“能力调优”阶段

随着模型能力、开发框架和工具协议的成熟，搭建一个可运行的Agent框架已不再是主要瓶颈。当前真正决定智能体产品竞争力的，不再是“能不能跑起来”——模型能否调用工具、能否完成多步交互、能否接入业务系统，而是Agent能否在真实业务中反复、稳定、安全地把任务做好。

以业务规则约束下的工具交互基准τ-bench为例，GPT-4o在零售任务上单次执行成功率（pass¹）为61.2%，而要求同一任务连续八次执行全部成功的严格指标（pass⁸）低于25%[1][5]。“一次做对”与“稳定交付”之间存在数倍差距，而这一差距无法通过更换更强的模型自动弥合。长流程任务基准同样表明，完成大量中间步骤不等于交付完整结果。换言之，智能体的能力短板已经从单点模型能力，转移到“模型—运行支撑—执行环境”协同形成的端到端交付能力上。

与这一转变相应，行业内形成了两个重要的方法论共识，本指南直接建立在它们之上：

1. Agent的端到端能力由模型、Harness、执行环境三层共同形成[2]。模型负责决策，Harness（运行支撑层）负责上下文、工具协议、状态、权限与运行控制，执行环境负责实际承载动作。任何一层失效都会表现为“Agent不好用”，但三层的优化手段、成本与责任主体完全不同。
2. Harness Engineering已成为独立的工程学科[3]。上下文架构、架构约束、自验证循环、上下文隔离、熵治理、可拆卸性等工程机制，被证明对生产可靠性有系统性影响；仅靠提示词技巧无法替代这些机制。

因此，“调优”不再是零散的改提示词、换模型，而是一门需要方法论、流程、数据资产和组织分工共同支撑的工程活动。本指南的编写正是对这一阶段的回应。

### 1.2 医疗场景的特殊性：通用方法论必须经过医疗化改造才能落地

将通用智能体调优方法直接套用到医疗场景是不充分的。医疗智能体，尤其是与影像设备、扫描协议、检查流程深度耦合的智能体，存在四个显著的特殊约束：

- 高风险性。扫描协议推荐、参数调整等输出直接影响患者检查质量与安全。错误的协议组合或参数不是“体验问题”而是“安全事件”。因此安全约束必须由系统强制实施，不能依赖模型自律，也不能用其他指标的高分抵消。
- 强证据要求。医疗输出必须可回溯到证据：影像依据、工具执行结果、知识库条目、指南条款。“回答看起来合理”不构成可信性；评估必须覆盖证据链，而非仅评价最终文本。
- 端侧部署约束。医疗智能体大量运行在设备端侧，模型规格受端侧算力制约（端侧Qwen 9B/35B系列的初步选型），上下文窗口、时延、模型更新成本都与云端场景不同。大模型堆叠、多模型反复复核等云端常用手段在端侧受到硬约束。
- 证据成熟度的严格区分。仿真环境通过、回顾性数据评测、专家评审、前瞻性临床验证是完全不同的证据等级，混用会导致对产品成熟度的严重误判。医疗影像智能体文献的系统梳理同样表明：离线Benchmark高分不证明临床收益，模拟控制台操作成功不代表真实设备采集成功[4]。

本指南的全部方法均经过上述约束的医疗化改写，并在涉及外部案例处显式标注证据边界。

### 1.3 内部现状：架构已成形，能力待调优

平台小U已完成基本框架建设，形成了清晰的分层架构：

- 交互层：uCopilot经AG-UI协议接入；
- 编排层：Host Agent（Orchestrator）统一编排，挂接Planning Subagent与Classifier Subagent，并通过A2A协议连接Remote Subagent与Local Subagent；
- 模型层：外接模型服务，端侧LLM初步选型Qwen 9B/35B系列，ASR/TTS语音模型完成初步选型，意图/快速决策专用小模型选型待定；
- Harness组件：Context（Runtime Context静态配置）、State（短期记忆）、Store（长期记忆）、Prompts、Tools（经MCP接入Service）、Skills；
- 可观测基础：已具备Langfuse追踪能力，问题上报可携带追踪码。

BU垂域智能体已形成覆盖CT、MR、MI、US、XR、RT等产品线的项目矩阵。各项目成熟度差异明显：CT协议推荐智能体（81H2）已完成安全护栏一期（LLM版/纯规则版红区护栏）与基于知识库的个性化方案一期，二期多协议组合推荐推进中；CT扫描参数推荐智能体（81H3）处于护栏方案设计中；超声、RT技师智能体处于安全与个性化需求梳理阶段；DSA介入医生智能体已完成一体式/分体式架构决策；MR明确1.X采用规则式智能体方案。

问题已经开始暴露，且具有明显的结构性特征。平台小U已记录调优需求包括：上下文理解能力弱（“创建任务清单”未按清单范式输出且追问无效）、系统信息过度披露（skills参数与实现代码被完整输出）、UI组件调用失败（配置页面无法直达目标面板）、超出功能范围输入识别不足（部分未拦截）、技能调用不完整（“修改配置”只打开界面未执行修改）、知识建议到技能调用的链路缺失，以及对象级工作流操作、条件检索与批量归档两类任务执行问题。

对这批问题逐条初步归因可以发现：绝大多数问题出在Harness层而非模型层——上下文组织、信息披露控制、工具协议粒度、护栏覆盖、动作链路完整性。这与行业经验一致，也与本指南的结构对应：Harness调优（Chapter 2）是当前投入产出比最高的调优方向，模型训练（Chapter 3）必须以严格归因为前提，避免用高成本的训练去解决本可由工程机制解决的问题。

### 1.4 现状的本质：调优工作的“四个不统一”

综合上述现状，当前调优工作的核心障碍不是缺少单点技术，而是缺少统一规范，具体表现为：

1. 归因不统一。同一问题，不同工程师可能分别归因为模型不行、提示词没写好、工具有问题。归因层次不同，后续所有动作都会偏离。没有“先环境、再Harness、后模型”的统一归因纪律，就会出现用训练弥补工程缺陷、用换模型掩盖协议含混的高成本低效路径。
2. 方法不统一。改Prompt、加护栏、调工具、训模型之间缺乏准入条件与选择依据，优化动作依赖个人经验，无法沉淀为团队能力。
3. 验证不统一。“跑几条例子感觉变好了”与“同条件对照实验＋回归集验证”之间存在本质差距。没有固定任务集、固定评估口径和版本记录，调优收益无法确认，退化无法发现。
4. 资产不统一。Badcase散落在个人记录中，修复经验随人员流动流失；轨迹、判据、失败模式没有成为可复用的数据资产，同类问题反复从零排查。

本指南即针对这四个“不统一”建立统一规范：统一归因（Chapter 1）、统一方法（Chapter 2/3）、统一验证（Chapter 5）、统一资产沉淀（数据飞轮机制贯穿全文）。

## 3. 适用范围与使用方式

适用范围：

1. Harness层优化：提示词、上下文与记忆、知识库、工具调用方式（MCP）、Skill、多Agent编排（Host Agent / Planning / Classifier / Remote/Local Subagent）、安全护栏、决策方式选择；
2. 模型训练调优：SFT、Agentic RL、蒸馏，以及端侧部署约束下的模型体系设计与端云协同；
3. 在线自进化：以受控方式将运行经验沉淀为可复用资产，候选生成不等于自动上线；
4. 数据飞轮支撑：数据构造、模拟仿真、测评。

不适用范围：运行环境（容器、沙箱、工作流运行环境、设备端工程实现）的具体优化技术，本指南仅界定其归因边界（Chapter 4）。

三种使用路径：

- 问题驱动路径（最常用）：遇到具体问题 → 携带Langfuse追踪码或BaseCase记录 → 按Chapter 1.2归因 → 进入Chapter 2或3对应节 → 用章末检查清单自检 → 按Chapter 5验证 → 修复后样本入回归集；
- 系统建设路径：新建或重构智能体 → 按Chapter 1建立目标体系与责任分工 → 按Chapter 2设计Harness基线 → 按Chapter 5建立数据集与门禁 → 视条件启动Chapter 3训练；
- 评审路径：评审调优方案或发布申请 → 使用Chapter 1.8、5.9检查清单 → 核对附录A模板完整性。

## 4. 编写、评审与维护机制

1. 版本化。指南整体版本与各章版本统一管理；重大方法变更（归因流程、门禁原则、数据规范）升级主版本，案例补充与文字修订升级次版本。
2. 反馈入口。使用者发现问题，汇报给小U主owner与AIC智能体团队，共同分析界定问题，AIC智能体团队负责修订与发布。
3. 与实践的同步。每轮调优实践结束时，负责人必须回答：本指南哪条被验证有效、哪条需要修订、产生了什么新经验。该记录与黄金集、回归集的版本变更同步归档。
4. 指南自身的演进。指南修订稿经评审后发布，历史版本可追溯，重大变更附迁移说明。
