## 2. SOP 阶段与停留条件

| 阶段 | 需要什么 | 用户操作 | 可产出什么 | 不能继续时 |
| --- | --- | --- | --- | --- |
| S0 确认案例 | Session / 关键词、项目与时间范围 | 选 Trace，确认现象和预期，附相关轮次 | 排查范围、主要 Trace、问题描述 | 扩大检索范围或补充定位信息 |
| S1 拆解运行 | Observation、父子关系、时间、输入输出 | 确认外层边界、N次循环与环节映射 | 确认的循环/环节与原始引用 | 显示未映射记录和缺口，可先探索 |
| S2 定位异常 | 循环/环节、预期、关键词/状态 | 选一种方法，核对实际与预期；可主动调用一次LLM辅助 | 用户确认的候选循环/环节、受影响位置 | 补预期、补记录或换入口 |
| S3 核对上下文 | 选定模型调用的实际输入输出 | 看完整上下文，逐项判断三标准 | 判断、依据、证据引用和未决项 | 保留证据不足，不把摘要当原文 |
| S4 走核心决策 | 关键步骤证据、三标准结果 | 逐节点作答，按需调用一次 LLM 辅助 | 一个或多个候选优化对象 | 创建补充任务或保留待确认分支 |
| S5 形成记录 | 路线、候选与证据 | 排序候选，写下一步验证，保存 | 可回查的排查记录 | 可保存未完成记录 |

阶段是导航，不是禁止探索的硬关卡。可查看后续标准，但下游依赖缺失时不能显示为已确认结论。S3 的判断属于 S4 第一个决策节点的输入，不需要用户重复填写。

## 3. Trace、循环、步骤与六环节

### 3.1 以 p7 图4 作为教学层级依据

图4明确标出“一轮交互可包含多次循环，先按循环粒度定位异常”：①在 Loop 前，②–⑤位于 Loop 内，⑤的结果与状态回到下一次②，⑥位于本轮结束时。

```text
Session：可以关联多次交互的 Trace
└─ Trace：本案例中的一次交互运行
   ├─ ① 请求接收与任务状态读取
   ├─ Agent Loop
   │  ├─ 循环1（主定位步骤1）
   │  │  ├─ ② 上下文准备与组装
   │  │  ├─ ③ 模型调用与返回
   │  │  ├─ ④ 动作校验、调度与执行（按需）
   │  │  └─ ⑤ 结果处理、校验与状态更新
   │  ├─ 循环2（主定位步骤2）：再次执行相关环节
   │  └─ ……
   └─ ⑥ 输出处理、交付与展示
```

这表达的是教学和排查关系，不是保证所有 Agent 的真实 Trace 都按此边界埋点。Langfuse 的 Trace 是应用定义的一次请求或操作，Observation 保留实际结构；部署映射需单独确认。

### 3.2 统一“步骤”的粒度

- 主定位步骤采用**一次循环**，UI统一称“循环1、循环2……”，先缩小到循环，再展开②–⑤检查具体环节。
- 六环节是运行职责分类，不能对每次循环再套一份①–⑥；一次循环包含②–⑤中实际发生的部分。
- 原稿 p6–7 的伪代码把加载说明、组装上下文、模型决策等具体操作称为“步骤”，p13 又把模型决策到动作反馈的组合称为“步骤”。本站把前者称为“环节中的具体操作”，后者明确映射到循环，避免两种粒度混用。
- ①/⑥作为外层可选位置保留；如果异常在接收或交付，就直接定位该位置，不制造一个空循环来容纳它。
- 决策的完整上下文、模型输出、动作参数和反馈都应在所属循环内联动。决策前的上下文准备属于该次模型调用，不按 p13 字面上的调用开始时间把它漏在外面。

### 3.3 原始记录到教学层级的映射

- 一个环节可以映射多条 Observation，如②中既有记忆取回又有上下文组装；一个④也可能有多个工具调用或重试。
- 容器可覆盖多次循环，不能当作一个普通操作复制到每次循环；原始ID和层级始终保留。
- 最终模型直接回答时④可以不发生，⑤按实际的处理/校验记录展示；无埋点时标未记录，不补造。
- 请求处理失败、循环未完成、流式输出、并行或子Agent路径按实际依赖表达；六环节不承诺全局严格串行。
- 循环边界或环节无法识别时保留未分类记录、标记待确认，允许人工调整并记录映射版本。仅有时间先后不能证明因果或循环归属。
- 不通过 `SPAN`、`TOOL` 名称判断业务必然正确或是否产生语义，也不推断内部部署一定支持官网全部记录类型。

## 4. 三种定位入口与共用循环

| 入口 | 操作 | 要保留的证据 |
| --- | --- | --- |
| 关键词 | 搜索 Skill、工具、实体、动作及相关词，定位命中的循环/环节 | 命中字段、原文片段、搜索范围；相关词由用户确认 |
| 异常状态 | 查看报错、超时、重试、失败，定位相关循环/环节 | 原始状态、错误内容、时间与重试；不把业务不符伪装成 ERROR |
| 从头对比 | 写明预期，从①和首次循环开始沿相关执行链检查 | 循环/环节的预期、实际、符合与否、第一处可见偏差 |

共用核对循环：查看当前循环的实际输入输出 → 展开相关②–⑤ → 记录预期 → 用户判断是否符合预期。遇到①/⑥偏差直接检查该位置。

- 正在逆查异常：若当前循环/环节按有效约定执行，异常可能由上游输入传来，沿有证据关联的上游继续核对；不直接宣布上游有问题。
- 正在从头对比：符合预期则查看下一循环，必要时展开其中环节；发现首次偏差后，核对关联上下游。
- 当前循环/环节不符合预期：标为候选关键位置，再按需确认下游受到什么影响。
- 无法判断：记录缺失材料或未明确的预期。可以换入口或补信息，不自动编造核对结果。

排查可产出多个候选循环及环节。标记“受影响”不等于排除该位置还有其他独立问题。

核对笔记保持轻量：当前循环/原文引用自动关联，正常位置可只选择结果；不符合或证据不足时说明偏差/缺口。切换定位入口保留各自输入和既有核对，不强制重做。

### 4.1 可选 LLM 辅助定位（产品建议）

建议在 S2 提供按钮“LLM 辅助定位”，默认不调用。三种方法仍是原 SOP 的三个入口，LLM 是它们的辅助能力，不是新增的第四种方法或必经步骤。

| 使用场景 | LLM 适合协助什么 | 程序/用户仍负责什么 |
| --- | --- | --- |
| 关键词 | 从描述建议相关词，解释命中记录可能关联哪个问题 | 程序查实际命中，用户选择并核对 |
| 异常状态 | 解释错误传播，建议回查有记录支持的上游 | 程序列真实状态，用户确认关键位置；不能凭ERROR断根因 |
| 从头对比 | 对照已确认预期，建议首个可见偏差、后续影响与缺口 | 用户给业务预期，核对建议并提交判断 |

请求范围可为当前循环及必要上下游，或用户选定的多个循环。返回候选循环ID/环节、偏差说明、支持和反向证据、建议回查方向、缺失信息。范围不完整时明确只能说明该范围内的可见偏差。

候选点开能回原文；“加入待核对”只创建待查项，不自动确认异常。与后续“是哪一类优化对象”的核心决策分开。符合性比较需要用户明确预期，材料不足时返回待补项，不编造应有行为；搜索词建议、已有错误解释可先进行。

## 5. 上下文拆解与三标准

### 5.1 六类来源

按 p4 模型输入图：任务与用户输入、系统角色与规则、工具与技能说明、记忆与外部知识、会话历史与任务状态、工具调用与执行反馈。

分类视图只辅助阅读，不重新组装或改写原始模型输入。每个片段保留 Observation ID、字段路径、角色、顺序和原始内容位置。混合来源允许多标签；未知来源保留未分类。多模态附件、引用文件、截断及脱敏影响都要标出可见范围。

### 5.2 用户逐项判断

| 标准 | 采用原稿 p5 表2的口径 | 页面提问 |
| --- | --- | --- |
| 齐全 | 决策所需要求、约束、历史、状态、反馈是否实际进入输入 | 这个步骤需要知道什么？哪些确实出现在输入里，哪些缺失？ |
| 精准 | 正确、相关且精简，保留必要事实，减少无关、重复或失效材料 | 哪些内容错误、失效、冗余或干扰？有何依据？ |
| 一致 | 关键事实、规则、状态衔接，使用更新后的有效信息 | 有冲突吗？哪个版本或状态有效？前后如何对应？ |

每项为“满足 / 不满足 / 证据不足”，三个答案同时可见，共用同一调用/引用；当前项可追加依据。满足时备注可选，不满足或证据不足时记录偏差/缺口。判断齐全还需要已知任务要求，不能仅因`input`字段非空就通过。

聚合方式：三项均满足才进入输入检查通过；任一不满足可以检查 Harness，同时保留其他未决项；没有不满足但存在证据不足时，保持待补充。不能把“LLM 认为满足”直接转换为用户答案。

## 6. 核心决策图的节点规则

依据原稿 p5 图3与表2；以下节点 ID 是本站建议的数据标识。

| ID | 用户要判断的问题 | 是 | 否 |
| --- | --- | --- | --- |
| D1 | 本次输入齐全、精准、一致吗？ | D2 | H1 |
| H1 | 本步需要跨轮次使用的历史信息取出来了吗？ | H2 | 候选：记忆 |
| H2 | 所需 Skill 说明正确组装进输入了吗？ | H3 | 候选：Prompt |
| H3 | Skill 调用判断、顺序和步骤正确吗？ | H4 | 候选：Skill |
| H4 | 工具执行过程与返回符合约定吗？ | 候选：架构设计 | 候选：工具 |
| D2 | 模型判断、选择与性能满足任务要求吗？ | E1 | 候选：模型，继续分辨方向 |
| E1 | 运行环境与安全监测正常吗？ | 候选：架构设计 | 候选：运行环境与安全监测 |

模型方向按原图分辨：基础能力不满足 → 选型；有基础能力但业务判断习惯未对齐 → 业务训练；判断正确且主要问题是速度/部署成本 → 量化压缩。单次调用的失误只能形成候选，不能直接证明应训练或更换模型。

H1 等条件不适用时允许“本任务无需该机制”，写明依据后跳到下一检查项，不把未调用记忆当作记忆故障。

**网站新增状态：证据不足。** 每个节点都允许暂不作是/否判断，创建补充任务。原图 E1 将“是 / 暂不能确认”都指向架构设计；本站建议把“暂不能确认”的架构方向保留为待核查候选，同时显示环境证据缺口，不与已证实环境正常的路径合并。这一表达调整需随 SOP 版本记录。

节点检查顺序不意味着发现一个候选就不能保留其他证据。用户可从其他关键步骤新建一条决策路径，最终汇总候选。

## 7. 按需调用一次 LLM

1. 用户选择用途：S2“辅助定位”，或 S3/S4“辅助当前判断”，例如检查循环3的模型输入是否精准。
2. 展示范围和将发送的证据：所选Trace与循环/环节、模型调用、必要上下游、用户已确认的预期、适用SOP条款；允许调整范围。
3. 定位返回候选位置与待查建议，判断返回建议答案；都保留引用、反向证据、缺失信息。材料不全时允许返回无法判断。
4. 用户查看原文，采纳、修改或忽略意见，再显式提交自己的答案。

辅助模型不能更改原始运行数据、擅自补全看不见的上下文，也不自动把一个节点扩展成连续多轮代理排查。辅助记录绑定当时的证据版本；证据变更后标为旧意见。

## 8. 补充、回退与结果反馈

- 补充任务写明缺什么、为何需要、影响哪个判断。用户可以补业务预期、原始日志/材料或操作结果；新材料标记来源，不能伪装成 Langfuse 原始记录。
- 服务器保存调查状态与人工答案。用户改变主 Trace、步骤拆分、证据或上游答案时，相关下游标为待复核，不静默删除历史。
- 结果区分候选关键步骤、受影响步骤、候选对象、证据缺口和下一步验证。
- 验证遵循保持其他条件稳定、检查局部和完整任务、检查新增异常。无改善重新核查归因，局部改善继续查其他因素。
- 教学案例可以展示经审核的参考路径；真实案例反馈以证据覆盖、矛盾和遗漏为主，不设置未经核验的唯一正确答案。
- 确认系统不存在所需机制时可以转建设性需求；缺记录或接口读不到，不等于系统没有能力。
- 进入课程、切换原文视图、查看完整图不改变业务判断。返回时恢复循环/环节、记录位置与草稿；源版本变化再提示复核。
- 非模型位置没有关联调用时继续保留执行证据及适用性/缺口，不强填三标准或自动给出对象。用户可以补充材料或记录待核对候选。

## 9. 材料核对：不宜直接变成案例标准答案

1. **p15–16 的 CT-02 证据冲突。** 展示的实际输入包含“用户：CT-02今天有什么排班？”，结论却称模型看不到 CT-02。需核对真实调用输入；不能据该样例直接判信息缺失。
2. **历史压缩归属不一致。** p6 将已取回后在压缩/状态传递中丢失的信息归架构设计；p16 又落到记忆/历史压缩。需区分未取回、取回后丢失、记忆内容本身错误等条件，再确定对象口径。
3. **定位入口名称需核对。** p14 以业务回复异常进入“状态异常”方法，展示记录未明确给出错误状态。正式案例应区分观测平台报错与业务预期不符。
4. **“步骤”一词粒度混用。** p6–7 的具体操作、p7 图4的循环、p13 的组合步骤表达不同。网站以图4为主，统一显示“Trace → 循环 → 环节 → 原始记录”，①/⑥单列；案例回放同步这一口径。

这些问题不阻塞页面与接口能力设计。处理完成前保留材料原文和审校标记，不发布确定性归因或自动评分。
